# 接入点与网页会话的共享元数据锁

接入点触发、投递与租约使用 Postgres，但网页的工作区、会话和任务索引仍是 `CODING_DATA_DIR` 下的 JSON。两个服务进程分别领取不同触发时，原来的实例级 `sync.Mutex` 不能防止彼此覆盖 `sessions.json`。

现在 `Store` 的工作区、会话、任务、环境配置、快照写入与删除，在现有实例互斥锁之内，再取得同一个 `.metadata.lock` 的 OS 排他锁。锁只覆盖 JSON 的读改写，不覆盖 Runtime、GitHub 或邮件网络调用。Unix 使用 `flock`；Windows 使用同步 `LockFileEx` 的字节锁。锁文件始终保留，文件句柄关闭或持有进程退出时由 OS 释放，不靠 PID 或过期时间删除锁文件。

`Sessions` 是唯一额外锁住的读取入口，因为它调用的 `readSessions` 会清除旧版本误写的私人配置并重写列表。内部 helper 不重复取锁；普通只读方法继续依赖原子替换读取完整文件。账号与 OAuth、workspace-operation journal 等其余文件没有借此次改动扩展存储模型。

## 部署条件

- 所有读写同一批元数据的 coding-web 进程必须指向同一份数据目录，并能访问同一个锁文件。每个副本各挂一份独立目录不构成共享存储。
- 多节点共享卷必须确实支持跨客户端文件锁与原子替换，且所有副本使用兼容的权限和服务 UID。启用本地锁模式或不传播 advisory locks 的 NFS/SMB/FUSE 配置不满足条件。
- 此锁协调项目、会话和任务索引的读改写，不把整套 coding-web 的所有 JSON 记录变成事务数据库；也不提供进程崩溃时跨多个文件的事务回滚。
- 不要在运行中删除、替换或轮换 `.metadata.lock`，否则旧进程和新进程可能锁住不同 inode。
- 上线多节点前，需在实际共享卷上运行两个进程的并发写验证。本次验证在本机文件系统完成，没有验证生产共享卷的锁传播。

## 已验证

临时探针（验证后已移出仓库）以 `-race` 运行通过：

1. 两个独立 `Store` 实例同时各追加 30 条会话、任务和项目，最终三类各 60 条，无丢失。
2. 两个独立进程同时各追加 30 条，最终三类各 60 条；锁文件保留。
3. 杀掉持锁子进程后，另一进程可继续写入，无陈旧锁清理操作。

现有 Session/Store/Personal 回归（含 Chromium）、Linux amd64 与 Windows amd64 的服务端编译通过。记录见 `evidence/entry-points-20261110/metadata-lock-probe.log`。
