# 接入点计划

> 状态：2026-11-10 设计稿，没有实现。第 10 节各条人已定（2026-11-10，都按建议），EP-01 起可以开工；EP-05 开工前还要定邮件怎么收。
> 来源：人提的要求（除网页外，任务可以由别的地方触发；都能在网页上看；结果回到触发的地方；接入点可扩展），对照本仓库已有的 GitHub 评论触发（G-06，`docs/plan/github-app.md`）与参考实现 dsh-superagent（第 11 节）。

## 1. 目标与范围

- 网页之外再有几种**接入点**能起任务：GitHub 的 @ 评论（已有，写死）、定时任务、服务器告警、邮件，以后还能加。
- 不管从哪儿起，都是一个普通的会话加一个 Runtime Task：网页上照常看进度、追加指令、回答确认、审阅改动。
- 任务到了要对外说话的时候（已受理、要确认、有结果、失败），按接入点的**出口**多做一步投递，比如在触发的 Issue 下回帖。
- 加一种接入点时，开发者必须同时交代清楚触发逻辑、出口，以及哪些留给用户配（第 6 节的规格表）。
- 做完之后用户才在界面上决定连不连、怎么配；所以“类型”（代码）与“连接”（用户的配置）分开。

不在范围内：Runtime 不改（全部经现有的 Task API、Workspace API 与 JWT）；IM（飞书、Slack）这一版不做，但接口要放得下。

名字：本仓库里 `sources.go` 的“来源”指任务引用的文件资料，与这里无关。这里一律叫接入点，代码里用 `entry`，不用 source。

## 2. 已有与缺失

| 块 | 已有 | 缺 |
| --- | --- | --- |
| 入站 | `internal/github` 的收件箱（Postgres）：验签、按 delivery 去重、退避重试、死信、重放、对账 | 只认 GitHub 的 Webhook；没有轮询与定时两种入口 |
| 触发 | `githubtrigger.go`：解析 @ 评论、核对写权限、对应到账号、限流与预算、起会话与 Task、等确认、推送开 PR | 全部写死在 GitHub 上；记录在 JSON 文件（`github-triggers.json`），单副本 |
| 投递 | `notifyTrigger`：按状态在 Issue 里回复，`Notified` 记下说过的状态，失败下一轮再说 | 只有 GitHub 回帖一种；没有独立的投递记录、重试上限与死信 |
| 用户配置 | 无：触发条件、每仓库每小时 3 次与 5 美元都写死在代码里 | 连接的记录、配置表单、开关 |
| 界面 | 触发起的会话与普通会话一样能看 | 会话上不显示从哪儿来、投递到哪儿、投递成没成；没有“接入点”页 |

## 3. 概念与流程

| 概念 | 是什么 | 谁定 |
| --- | --- | --- |
| 接入点类型 | 一种接入点的代码：怎么收、怎么认人、怎么组指令、默认从哪儿回 | 开发者 |
| 出口 | 一种投递方式的代码：怎么渲染、怎么发、怎么保证不发两遍 | 开发者 |
| 连接 | 用户对一个类型的一份配置，属于一个账号、绑一个工作区。新建时什么都不接收，配了才生效 | 用户 |
| 触发 | 一条不可变的事件，带稳定的 ID；同一个 ID 只起一个任务 | — |
| 运行 | 一次触发起的会话与 Task，以及它走到哪一步 | — |
| 投递 | 把一条消息写到一个出口的一次动作，单独记录、单独重试 | — |

```text
外部事件 ─▶ 收件（验签、去重）─▶ 翻译成触发 ─▶ 准入（连接、身份、条件、限流、预算）
                                                    │拒绝：记下原因，回不回话按类型的规定
                                                    ▼
                                      会话 + Task（网页上照常可见）
                                                    │状态变化
                                                    ▼
                                      发件箱 ─▶ 渲染 ─▶ 出口（回帖、回信……）
```

网页创建是同一条路上的特例：没有收件与准入，出口只有网页本身。

**入口与出口分开。** GitHub 评论与邮件有“原处”可回；定时任务与告警没有。所以类型只声明默认出口，连接上可以换、可以加（比如定时任务的结果发成邮件，或发到某个 Issue）。

入口有三种形态，都落进同一张收件箱：推送（对方调我们的 Webhook）、轮询（我们去拉）、定时器（到点自己生成）。

## 4. 接口

```go
// Kind 是一种接入点。实现放 internal/entry/<名字>。
type Kind interface {
    Name() string                                   // 稳定的标识，进触发 ID、连接记录与指标的标签
    Schema() Schema                                 // 用户可配的字段、默认值与上下限；界面按它生成表单
    Ingest(ctx context.Context, in Inbound) ([]Trigger, error) // 验签或拉取，翻译成触发；不认识的一律丢
    Admit(ctx context.Context, c Connection, t Trigger) Admission // 认人、核对条件；限流与预算由框架统一做
    Compose(c Connection, t Trigger) TaskInput      // 指令与资料分开；外部内容只进资料块
    DefaultSink() (sink string, addr Address)       // 没有原处可回的返回空
}

// Sink 是一种出口。
type Sink interface {
    Name() string
    Phases() []Phase                                // 支持哪几个阶段：accepted、question、result、failed
    Render(o Outcome, p Phase, lang string) Message // 确定的模板，不调模型
    Deliver(ctx context.Context, c Connection, a Address, m Message, key string) error // 按 key 幂等
}
```

框架（`internal/entry`）负责各类型都一样的事：收件箱、去重、找连接、限流与预算、起会话与 Task、盯 Task 的状态、发件箱、重试与死信、指标。类型只写自己特有的那部分。

## 5. 投递

**不做成 Runtime 的 Hook，也不做成任务的最后一个节点**，做成 coding-web 里的发件箱，由 Task 的状态变化驱动。原因：

1. 任务被取消、超预算、等审批、失败时走不到“最后一步”，但来源同样要一条回复。
2. 出口的凭据（安装令牌、发信的密钥）在应用这边，Runtime 不保存，现在也是这样。
3. 回帖失败不该重跑任务。投递单独重试，任务的结果不受影响。
4. 在任务里对外发帖是不可逆的写：按 Runtime 的规则每次都要过 gate，而且不自动重试。

“多执行一步输出”拆成两步：任务产出通用的成果（网页上看到的就是它），出口的模板再把它渲染成回帖或邮件。要让成果里带上出口要的东西（比如给邮件的一段摘要），由 `Compose` 在指令里写明，不另外调一次模型。

- 阶段：`accepted`（已受理，带网页上这个会话的链接）、`question`（要人确认或审批）、`result`、`failed`。
- 幂等键：`连接 ID + 触发 ID + 阶段 + 出口`。先落盘再发；发到一半进程没了，按键查对方有没有这条，查不出来的出口宁可不重发并标成“结果未知”。
- 重试：退避，5 次后进死信；死信在网页的会话上看得到，能手动重发。投递失败不改变任务的状态。
- `question` 怎么答：网页上永远能答；出口支持的（GitHub 的确认评论）也能在原处答，答的人要再过一遍准入。

## 6. 开发者定什么，用户定什么

每加一种类型，先填完这张规格表，评审过了才写代码。

| 开发者写死（安全与正确性） | 用户在连接上配（不超过平台上限） |
| --- | --- |
| 怎么验签或认证入站请求 | 开不开，绑哪个工作区（哪些仓库） |
| 触发 ID 怎么取（去重靠它，定了不能改） | 触发条件：关键词、标签、发件人名单、cron、告警级别与匹配 |
| 外部身份怎么对应到账号；对应不上怎么办 | 指令模板（定时与告警没有人写指令，只能用户先写好） |
| 过滤自己与别的机器人发的，防循环 | 预算与频率 |
| 外部内容一律当资料，不当指令 | 自主程度：只分析并回复、开草稿 PR、推送前要确认 |
| 权限上限：effect 上限、只推 `agent/*`、改工作流要确认 | 出口：回原处、换一个、再加一个；只发结果还是也发“已受理” |
| 被拒的触发回不回话（陌生人不回，不给刷屏的机会） | 语言 |
| 平台级的预算与频率上限，各字段的上下限 | |
| 支持哪些阶段，结果未知时怎么办 | |

用户配的每一项都要有保守的默认值；默认值合起来必须是“什么都不接收”。

## 7. 各类型的规格

| | GitHub @ 评论（已有） | 定时任务 | 服务器告警 | 邮件 |
| --- | --- | --- | --- | --- |
| 入口形态 | 推送（App 的 Webhook） | 定时器 | 推送（每个连接一个地址） | 推送或轮询（第 10 节第 4 条） |
| 认证 | `X-Hub-Signature-256` | 无入站 | 每个连接一个密钥：HMAC 或请求头里的令牌；只显示一次，服务端存哈希 | DMARC 通过，且发件人是账号里验证过的邮箱 |
| 触发 ID | 评论 ID | 连接 ID + 计划时间 | 连接 ID + 告警指纹 + 开始时间 | Message-ID |
| 触发者 | 评论的人：有写权限、已关联账号 | 连接的主人 | 连接的主人（事件是机器发的） | 发件人对应的账号 |
| 指令 | 评论正文 | 用户写的模板 | 用户写的模板；告警内容进资料块 | 主题与正文；附件进资料，有大小与个数上限 |
| 默认出口 | 原 Issue 或 PR 下回帖 | 无，建连接时必须选 | 无，建连接时必须选 | 同一个邮件线程里回信 |
| 这一类特有的 | fork 来的 PR 不跑；改工作流要确认（都已有） | 上一次还没跑完就跳过；重启后只补最近错过的一次；间隔有下限 | 同一指纹在一个时间窗内只起一个任务；“已恢复”不触发；默认只分析不改代码 | 不回自动回复的信（`Auto-Submitted`），自己发的信带上这个头；发件人对不上的一律丢，不回 |

出口这一版三种：`web`（永远有，不用发）、`github_comment`、`email`。往任意地址发的出站 Webhook 有 SSRF 的问题，放到以后。

## 8. 数据

与收件箱同一个 Postgres 库，接口照样隔开，测试用替身。

| 表 | 主要的列 |
| --- | --- |
| `entry_connections` | ID、租户、用户、类型、工作区、配置（JSON，按类型的 Schema 校验）、出口与地址、开关、密钥的哈希、创建与修改时间 |
| `entry_triggers` | 触发 ID（主键）、连接 ID、类型、状态、原因、会话 ID、Task ID、次数、收到时间；指令与外部内容只留到 Task 提交出去为止 |
| `entry_deliveries` | 幂等键（主键）、触发 ID、出口、阶段、状态、次数、下次时间、对方给的回执 |

触发的状态沿用 G-06 的：`accepted → running → [awaiting_confirmation → confirmed] → publishing → done`，另有 `refused`、`failed`、`expired`。后台用 `FOR UPDATE SKIP LOCKED` 领取并带租约，多副本不会重复起任务或重复投递。

## 9. 界面

- 会话上标出从哪儿来（类型与原处的链接）、投递到哪儿、各阶段投递成没成；死信能重发。“进行中”能按来源筛。
- 设置里加“接入点”一栏：列出各类型与自己的连接；新建连接的表单按类型的 Schema 生成，不为每个类型单写页面。
- 每个连接有最近的触发记录（收到、拒绝与原因、起了哪个会话），用户能看出为什么没触发。
- 两种语言。

## 11. 工作项与验收

顺序：EP-01 → EP-02 → EP-03 → EP-04，EP-05 最后。

### EP-01 框架，GitHub 评论迁成第一个类型

1. `internal/entry` 有第 4 节的接口与框架；`githubtrigger.go` 的逻辑迁成 `github_comment` 类型与 `github_comment` 出口，对外行为不变（G-06 的 8 条验收照样过）。
2. 触发记录从 `github-triggers.json` 迁进 Postgres；迁移可以重复执行，迁完旧文件不再读。
3. 同一个触发投递两次只起一个任务；两个副本并发领取，同一条只处理一次。
4. 投递单独记录：回帖失败按退避重试，5 次进死信；重试不重跑任务；同一阶段不发两遍。
5. 任务取消、超预算、失败时原处各有一条说明。

### EP-02 连接与界面

1. 没有连接时什么都不接收；关掉连接后新的触发被拒，跑着的任务不受影响。
2. 表单由 Schema 生成；超出上下限的值存不进去；别的租户的连接读不到、改不了。
3. 会话上看得到来源与各阶段的投递状态；死信能重发；连接上看得到最近的触发与拒绝原因。
4. 密钥只显示一次，日志、错误信息与接口的返回里找不到（断言）。

### EP-03 定时任务

1. 到点起任务；触发 ID 含计划时间，进程重启不重复起。
2. 上一次没跑完时跳过并记下；停机后只补最近错过的一次。
3. 没选出口的连接建不出来；结果按选的出口投递。

### EP-04 服务器告警

1. 密钥不对或缺：401，不落盘，不解析负载。
2. 同一指纹在时间窗内只起一个任务；“已恢复”不触发；成批的告警不会把预算打穿（超了记下并在出口说明一次）。
3. 告警内容只进资料块；带注入样本的负载不改变指令。
4. 默认的自主程度下任务不推送、不开 PR。

### EP-05 邮件

等第 10 节第 4 条定了再细化。先定的验收：发件人对不上或 DMARC 不过的不起任务也不回信；自动回复的信不触发；回信在同一个线程里；同一封信重复收到只起一个任务。

## 12. 依据

参考实现 dsh-superagent（`deepseek-ai/dsh-superagent-prototype`，2026-11-10 读了 README、`docs/001-domain.md`、`docs/008-cookbook.md`）。采用的：

- 类型与实例分开（它叫 Source kind 与 Source instance）；实例的默认值必须是什么都不接收。
- 事件翻译成不可变、带稳定 ID 的 Trigger，重复接受只产生一份工作；ID 一旦定下不能改。
- 回写是单独的一侧（它叫 Channel），地址由接入的一方定义。
- 配置表单由类型声明的字段生成，不为每个类型写界面。
- 外部的正文与元数据都是不可信的数据，不是授权。

没采用的：它不把不同来源上的身份对应到同一个人；这里要对应到账号，因为任务记在账号下、花它的额度。它用模型判断一批事件要不要开工（Eval）；这里的准入是确定的规则，要不要做由用户在连接上配的条件决定。

没有核对过、实现时要查的：Alertmanager 与 Grafana 的 Webhook 各自支持哪种认证方式与负载里指纹字段的名字；入站邮件服务给出的 DMARC 结果的形式。
