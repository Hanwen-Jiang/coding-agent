# Coding Agent 应用缓存接入（2026-11-10）

CACHE-01 原先接入 Runtime task-service 的事件流、限流和工作区读缓存。coding-web 的公开目录和 GitHub 权限仍使用进程内 map，本次补齐应用侧连接与缓存使用。复用 `libs/go-core/adapters/valkey`，业务代码仅依赖 Cache 接口，不引入新的 Go 依赖。

## 配置与启动

| 变量 | 行为 |
| --- | --- |
| `CODING_PROFILE` | `development`（默认）或 `production`；生产模式必须配置缓存地址 |
| `CODING_VALKEY_URL` | 支持 `valkey://`、`redis://` 和 TLS 的 `valkeys://`、`rediss://`；地址按凭据处理，不输出 |
| `CODING_CACHE_PREFIX` | 默认 `coding-web:`；不同环境使用不同前缀；拒绝 Runtime 默认的 `ar:` |
| `CODING_VALKEY_MAX_CONNS` | 默认 16，允许 1–256 |

只要配置了地址，启动必须通过 PING；错误不包含原始地址、口令或上游文本。连接池在应用退出时关闭。部署清单使用已有 `agent-runtime-valkey/url` Secret，同时设置生产模式；沿用同一个部署的缓存服务，应用数据通过独立前缀区分。缓存命名空间不是凭据级隔离，如需要独立管理权限应另外配置专用实例或 ACL。

## 缓存范围

| 场景 | 数据与有效期 | 失败处理 |
| --- | --- | --- |
| Skills/MCP 公开目录 | 公共响应；键包含资源 URL 和读取上限的哈希；TTL 10 分钟，单条最大 8 MiB | 回源获取，保留本机 singleflight 合并并发请求 |
| 目录上游保护 | 共享限流与 HTTP 429 冷却状态 | 使用本机保护，不因共享缓存故障完全失去限流 |
| GitHub 仓库权限 | 租户、用户、仓库绑定的权限元数据；TTL 60 秒 | 重新向 GitHub 核验，不使用本机旧权限兜底 |
| GitHub 权限失效 | 随机 generation 版本，TTL 24 小时；安装/授权相关事件更新版本 | 失效失败由事件处理路径报告并重试 |

缓存操作设置短超时，不让缓存故障拖长外部请求。权限条目的键包含读取时的 generation；事件失效后，进行中的旧请求只能写回旧版本键。generation 丢失后生成新的随机版本，不回到固定初始版本，避免缓存淘汰后重新命中旧授权。

共享缓存只存可重建数据，所有写入有 TTL。生产实例应保留有界内存与淘汰策略，避免大量公开目录响应无限占用内存。共享模式不使用本机结果缓存覆盖远端状态。

## 不改变的存储边界

- 浏览器会话、账号、项目和 GitHub 自动触发记录仍按现有方式保存；本次不把它们搬进可淘汰缓存。
- Runtime JWT、GitHub App JWT、OAuth 用户令牌和安装令牌不写入 Valkey。
- Runtime SSE 仍由 Task API 提供，coding-web 不另建事件权威源。
- Webhook PostgreSQL 收件箱和应用其他文件状态不因缓存接入而变成同一套分布式存储；部署仍为一个 coding-web 副本。

## 验证

- 两个独立缓存客户端共享数据、TTL 到期、删除与前缀隔离，使用本地临时认证 Redis/Valkey 验证，不接生产缓存。
- 目录跨实例命中、并发请求合并、缓存故障回源、不同读取上限键隔离。
- 权限缓存的租户/用户隔离、事件失效、失效后旧请求写回不会重新授权、缓存故障时实时核权。
- 生产缺少配置、错误口令和错误地址均拒绝启动，错误不泄露连接凭据。

代码和部署清单的更新不等同于线上已部署；上线需同时更新 coding-web 镜像及环境变量，并确认对应 Secret 可用。
